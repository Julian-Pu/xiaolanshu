# 06 · 消息队列异步化设计（演进方案）

> 本文回答一个问题：小蓝书**什么时候、在哪里、怎么**引入消息队列（Redis Stream / Kafka），以及如何从当前的同步事务平滑切换到异步，且不破坏接口契约。
> 结论先行：MVP 阶段不引入（同步正确且足够）；出现第 2 节的任一信号时，按本文 4→10 节落地。

## 1. 现状盘点（基于当前代码）

| 路径 | 当前实现 | 位置 | 同步的代价 |
|---|---|---|---|
| 点赞 | `INSERT likes` + `UPDATE posts.like_count+1` + `INSERT notifications`（同一事务） | `InteractionService.like()` | 1 次请求 = 3 次写；热帖计数行锁竞争 |
| 收藏 | 同上（collects / collect_count） | `InteractionService.collect()` | 同上 |
| 评论 | `INSERT comments` + `UPDATE comment_count+1` + `INSERT notifications` | `CommentService.add()` | 同上 |
| 关注 | `INSERT follows` + 双方计数 + `INSERT notifications` | `UserService`（关注逻辑） | 同上 |
| 发布 | `INSERT posts` + `post_count+1` | `PostService.create()` | 写放大有限，暂不动 |
| 信息流-关注 | **读时拉取**（JOIN follows 查关注者笔记） | `FeedService.feed("following")` | 无 fan-out 写放大，天然可扩展 |
| 信息流-推荐 | 全站热度 SQL 排序 | `FeedService.feed("recommend")` | 数据量大后排序变慢（改缓存/热榜） |
| 私信 | REST 轮询（conversations/messages 表） | `MessageService` | 实时性靠轮询；MQ 非主战场，实时化走 WebSocket |

**结论**：当前同步模型没有正确性问题，只有"规模上来后的性能问题"。异步化改造是**演进**，不是缺陷修复。

## 2. 触发信号（满足任一，开始改造对应部分）

| 信号 | 阈值参考 | 优先改造 |
|---|---|---|
| 互动接口写入 P99 抖动 / 写放大明显 | 单机互动 QPS > 800 或 P99 > 500ms | 通知 + 计数异步化 |
| 热帖点赞数并发写竞争 | 单帖互动 > 1 万次/分钟 | 计数合并（Redis → 定期落库） |
| 通知写入拖慢互动主流程 | 通知表行数 > 千万级 | 通知异步化 |
| 大 V 发布后粉丝"刷不到" | 单账号粉丝 > 1 万 且要求秒级可见 | 信息流 fan-out（push 混合模型） |
| 需要热榜重算 / 内容审核流水 / 离线回溯 | 出现批处理任务 | Kafka 消费者组 + 重放 |

## 3. 组件选型

| 维度 | Redis Stream（首选） | Kafka |
|---|---|---|
| 定位 | 轻量消息流，复用已有 Redis | 分布式高吞吐事件总线 |
| 运维成本 | 低（Redis 已有） | 高（broker 集群、分区管理、磁盘） |
| 消费者组 / 重放 | 支持（Group + XREADGROUP） | 完善（offset 管理、按时间回溯） |
| fan-out（多消费者组各自消费） | 支持，组数有限时够用 | 原生强项 |
| 推荐场景 | 通知、计数、中小规模 fan-out | 大 V fan-out、批处理、多团队多系统 |

**本项目路径**：阶段 1/2 用 **Redis Stream**（轻）；只有 fan-out 或跨系统事件成为硬需求时才上 **Kafka**。依赖升级仅为 `spring-boot-starter-data-redis`（Stream 操作）→ `spring-kafka`。

## 4. 异步化落点设计

### 4.1 通知异步化（最高优先级，先做）

**现状**：`InteractionService.notifyOwner()`、`CommentService.notifyUser()` 在业务事务内直接 `INSERT notifications`。

**改造目标**：业务事务只写自己的核心表（likes/comments/follows），通知由消费者异步写入。

**事件消息体**（Topic：`xls.notify`，JSON）：

```json
{
  "eventId": "like_1024_5_20260928T133000Z",   // 幂等唯一键
  "type": "like",                               // like | collect | comment | follow | system
  "receiverUserId": 1,                          // 通知接收者（笔记作者 / 被关注者）
  "actorUserId": 5,                             // 触发者
  "refId": 1024,                                // 关联对象 id（笔记 / 评论 / 用户）
  "content": "赞了你的笔记",
  "createdAt": "2026-09-28T13:30:00Z"
}
```

**消费端**：写 `notifications` 表；幂等见第 7 节。

### 4.2 计数异步化

**现状**：like/collect/comment 的计数在业务事务内 `UPDATE posts SET xxx_count ± 1`。

**改造目标**（两阶段可选）：

- **阶段 A（轻）**：计数更新改为**发送增量事件**（`xls.counter`：`{postId, delta, kind}`），由计数消费者聚合更新。互动事务只剩"写关系表 + 发事件"，写放大 3 次 → 1 次事务 + 1 次投递。
- **阶段 B（重）**：热帖计数走 Redis 合并：消费端 `INCR post:1024:like`，后台每 N 秒 flush 增量到 MySQL（防抖窗口 + 断电补刷）。

**读路径回退**：详情/信息流的 `xxx_count` 读取增加 Redis 缓存（`post:{id}:{kind}` 为未 flush 的增量，展示值 = MySQL 值 + 缓存增量）。**允许短时（秒级）不一致**，这是异步化的明确取舍，需在接口文档标注"计数展示为最终一致"。

### 4.3 信息流 fan-out（可选，仅大 V 场景）

**现状**：关注流是**拉模型**（读时 JOIN），单机到几万粉丝都成立，**默认保留拉模型，不需要 fan-out**。

**何时需要**：大 V 粉丝量级让"粉丝打开 App 时实时 JOIN"变慢。

**混合模型**：
- 普通用户：保持拉模型（`FeedService` 现状不变）；
- 大 V（粉丝 > 阈值）：发布笔记时发 `xls.feed.publish` 事件（`{postId, authorId}`），fan-out 消费者把 postId 写入每个粉丝的 Redis 收件箱（`inbox:{followerId}` 为 sorted set，score=发布时间）；
- 关注流读取 = 收件箱（已推送）+ 拉取（未推送部分）合并，按时间去重。

> fan-out 是全项目**最后**才值得做的一步，且可以永远不做——拉模型在绝大多数阶段都够用。

### 4.4 私信（MQ 非主战场）

- 实时推送是 **WebSocket** 通道（网关/IM 服务），不依赖 MQ；
- MQ 仅可选承担"离线消息投递"（用户不在线时挂起，上线后补推），属锦上添花，阶段 1 不做。

## 5. Topic 与消息契约总览

| Topic | 消息类型 | 消费者 | 幂等键 |
|---|---|---|---|
| `xls.notify` | NotificationEvent | 通知消费者 | eventId |
| `xls.counter` | CounterEvent（`{postId, kind, delta}`） | 计数消费者 | eventId（业务侧生成） |
| `xls.feed.publish` | PostPublishedEvent（`{postId, authorId}`） | fan-out 消费者 | eventId |
| `xls.dead` | 所有 DLQ 消息（原 topic + 原消息体 + 失败原因） | 死信消费者（告警/补偿） | — |

所有消息体统一包含：`eventId`（唯一）、`createdAt`、`source`（产生方模块）。

## 6. Outbox 模式（事务一致性的关键）

**核心问题**：不能在业务事务里"先发 MQ 再提交事务"——事务回滚时消息已发出，产生幽灵事件。

**方案**：事务内写 **outbox 表**（同库同事务），事务提交后再投递。

```
业务事务（@Transactional）
  ├─ INSERT likes                    ← 核心业务写
  ├─ INSERT outbox (event_id, topic, payload, status='pending')
  └─ COMMIT
        │
        ▼ 投递器（定时轮询 / 事务提交后同步发，二选一）
  发送到 Redis Stream / Kafka → 成功后置 status='sent'
        │
        ▼ 消费者：写 notifications / 更新计数（幂等）→ ack
```

**outbox 表设计**：

```sql
CREATE TABLE outbox (
    id         BIGINT AUTO_INCREMENT PRIMARY KEY,
    event_id   VARCHAR(64)  NOT NULL UNIQUE,   -- 业务侧生成，幂等基石
    topic      VARCHAR(64)  NOT NULL,
    payload    TEXT         NOT NULL,          -- JSON 消息体
    status     VARCHAR(16)  NOT NULL DEFAULT 'pending', -- pending | sent | failed
    retry_count INT         NOT NULL DEFAULT 0,
    created_at VARCHAR(32)  NOT NULL,
    updated_at VARCHAR(32)  NOT NULL,
    KEY idx_outbox_status (status, created_at)
) COMMENT='事务内写入的消息出口（Outbox）';
```

**投递器两种实现**：
- 简单：`@Scheduled` 每 1s 扫描 `pending` 批量投递（上限 500 条/批）；
- 进阶：应用侧注册 `TransactionSynchronization.afterCommit()` 投递 + 定时兜底扫描（防进程崩溃漏发）。

## 7. 幂等与去重

消费者**必须**幂等，原因：投递可能重复（at-least-once 语义）、消费者可能重试。

**做法 1（推荐，业务表自带唯一键）**：`notifications` 表增加业务唯一列：

```sql
ALTER TABLE notifications
    ADD COLUMN event_key VARCHAR(64) NULL,
    ADD UNIQUE KEY uk_notif_event (event_key);
-- 消费时：INSERT ... ON DUPLICATE KEY UPDATE event_key = event_key;
-- event_key = eventId（如 like_1024_5_...）
```

**做法 2（通用去重表）**：`processed_events(event_id PK, topic, processed_at)`，消费前 `INSERT IGNORE`，插入失败说明已处理过，直接 ack。

> 计数合并同理：`CounterEvent.eventId` 唯一，Redis 增量去重用 `SETNX event:{eventId} 1`（TTL 7 天），重复事件直接丢弃。

## 8. 重试与死信

| 失败类型 | 处理 |
|---|---|
| 瞬时失败（DB 抖动、网络） | 消费者本地重试 3 次（指数退避 1s/5s/30s）后仍失败 → 投递到 `xls.dead` |
| 业务失败（接收者不存在、数据被删） | 直接记录告警，丢弃（这类消息重试无意义） |
| 死信 | 消费者读取 `xls.dead`：告警（日志 + 指标）+ 人工/脚本补偿；补偿成功则写回业务 |

**监控指标**（对接 Prometheus）：
- `xls_outbox_pending`（积压数）、`xls_consume_latency_seconds`（消费延迟）、`xls_dead_total`（死信数）、`xls_notify_dup_total`（去重命中数，验证幂等生效）。

## 9. Spring Boot 集成（落地指引，阶段 1）

```xml
<!-- Redis Stream 方案（阶段 1/2） -->
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
</dependency>
```

**生产者（事务提交后投递，示意）**：

```java
@Transactional
public LikeResult like(long postId, long userId) {
    // ... 现有业务写（likes 表、计数）保持不变或改为事件 ...
    String eventId = "like_" + postId + "_" + userId + "_" + Instant.now().toEpochMilli();
    jdbc.update("INSERT INTO outbox (event_id, topic, payload, status) VALUES (?, 'xls.notify', ?, 'pending')",
            eventId, objectMapper.writeValueAsString(Map.of(
                    "eventId", eventId, "type", "like",
                    "receiverUserId", ownerId, "actorUserId", userId,
                    "refId", postId, "content", "赞了你的笔记",
                    "createdAt", Instant.now().toString())));
    return new LikeResult(true, count("likes", postId));
}
```

**投递器（示意）**：

```java
@Scheduled(fixedDelay = 1000)
public void dispatch() {
    List<Map<String, Object>> rows = jdbc.queryForList(
            "SELECT * FROM outbox WHERE status = 'pending' ORDER BY id LIMIT 500");
    for (Map<String, Object> row : rows) {
        String eventId = (String) row.get("event_id");
        try {
            redis.opsForStream().add(XRecord.create((String) row.get("topic"), payloadOf(row)));
            jdbc.update("UPDATE outbox SET status = 'sent' WHERE id = ?", row.get("id"));
        } catch (Exception e) {
            jdbc.update("UPDATE outbox SET status = 'failed', retry_count = retry_count + 1 WHERE id = ?", row.get("id"));
        }
    }
}
```

**消费者（通知落库 + 幂等，示意）**：

```java
@Component
public class NotifyConsumer {
    @EventListener // Redis Stream 消费者组监听
    public void on(NotificationEvent event) {
        try {
            jdbc.update("""
                    INSERT INTO notifications (user_id, actor_id, type, ref_id, content, is_read, created_at, event_key)
                    VALUES (?, ?, ?, ?, ?, 0, ?, ?)
                    ON DUPLICATE KEY UPDATE event_key = event_key
                    """, event.receiverUserId(), event.actorUserId(), event.type(), event.refId(),
                    event.content(), event.createdAt(), event.eventId());
        } catch (Exception e) {
            throw new RetryableException(e); // 走本地重试 → 死信
        }
    }
}
```

## 10. 分阶段迁移（灰度开关）

| 阶段 | 内容 | 开关配置（application.yml） | 回滚 |
|---|---|---|---|
| 0（现状） | 全同步 | — | — |
| 1 | 通知走 outbox + `xls.notify`；**计数仍同步** | `xiaolanshu.async.notify.enabled=true` | 关开关即回同步 |
| 2 | 计数改 `xls.counter` 增量合并（热帖 Redis 合并） | `xiaolanshu.async.counter.enabled=true` | 关开关 + 重算一次计数（已有 `seed` 重算 SQL） |
| 3 | 大 V fan-out（按粉丝阈值开关） | `xiaolanshu.async.fanout.enabled=true` + `threshold` | 关开关 + 清收件箱回拉模型 |

**灰度顺序**：先 5% 流量验证（通知延迟、计数偏差、死信数为 0），再 50%，再全量；每阶段观察 1~2 个发布周期。

**回滚原则**：所有开关默认 `false`（同步兜底），任何异常先关开关恢复同步，再排查异步链路。

## 11. 验收指标

| 指标 | 目标 |
|---|---|
| 互动接口 P99（写放大消除后） | ≤ 300ms |
| 通知消费延迟（事件产生 → 落库） | ≤ 2s（P95） |
| 计数偏差（MySQL vs 明细表重算） | 每 10 分钟重算偏差 = 0 |
| 死信率 | < 0.01% |
| 去重命中率（幂等验证） | > 99.9%（说明重复投递被正确拦截） |

---

**小结**：先 Redis Stream 做通知与计数；Kafka 只在 fan-out / 跨系统事件成为硬需求时引入；Outbox + 事件唯一键 + 消费幂等 + 死信四件套保证不丢、不重、可补偿。所有改造不改变 `/api` 接口契约，前端与 Android 端零改动。
